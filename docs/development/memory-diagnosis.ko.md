# 기억 기능 진단 보고서

작성: 2026-10-23 · 기준: `feat/next-update` · 비교 대상: 기억 보관함 확장 v2.1.1

이 문서는 **코드를 읽고 정리한 진단**이다. 실제 긴 채팅에서 토큰 사용량·속도를 재지는 않았다(미측정).
수정은 하지 않았다. 아래 "결정 필요"를 정한 뒤 작업한다.

## 1. 지금 엔진의 기억 구조

엔진에는 기억 계열 기능이 네 가지 있고, 서로 일부만 배타적이다.

| 기능                                        | 저장 위치                                   | 프롬프트에 들어가는 조건                                         |
| ------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------- |
| 통합 기억(`committedMemory`, 보관함 이식분) | 채팅 메타데이터 `committedMemory` 한 덩어리 | RP + 켜짐 + **고급 메모리 꺼짐**                                 |
| 기존 요약(`summary`/`summaryEntries`)       | 채팅 메타데이터                             | 통합 기억이 꺼졌을 때만                                          |
| 기억 회상(`enableMemoryRecall`, 벡터 조각)  | 메시지 임베딩                               | RP는 켰을 때, Convo는 기본 켜짐. **통합 기억과 무관하게** 들어감 |
| 고급 메모리(순정 `advancedMemory`)          | 별도                                        | 켜면 통합 기억·요약을 모두 끔                                    |

통합 기억의 흐름(`packages/server/src/services/committed-memory*.ts`):

1. 사용자가 "기억 정리"를 누르면 대기 메시지를 묶음(batch)으로 모델에 보내 요약·핵심(core)·사실(fact)을 받는다.
2. 사실은 종류(fact·promise·event·relationship·belief), 상태(current·resolved·uncertain), 진행도(약속), 공개 범위(audience)를 가진다.
3. 매 생성마다 `committedMemoryForPrompt`가 최근 메시지로 질의를 만들고, 글자 2-gram 겹침 점수(+ 임베딩이 있으면 코사인 0.35 이상)로 골라 넣는다.
4. 최근 30묶음은 요약, 300묶음까지는 core, 그 이전은 gist로 줄여 넣는다(`selectCommittedMemory`).

## 2. 문제점 (근거 코드 위치)

### 2-1. 컨텍스트 낭비

- **진행 중 사실은 질의와 상관없이 전부 후보가 되고, 개수 제한(topK)을 받지 않는다.**
  `selectCommittedMemory`에서 `reason: "current"` 항목은 기본 점수 2(약속 4)를 받아 항상 에피소드보다 먼저 예산을 채운다. topK 검사는 `reason !== "current"`에만 걸린다.
  사실이 쌓일수록 매 턴 같은 사실 묶음이 예산을 차지하고, 정작 관련 있는 과거 장면은 밀려난다.
  보관함은 "항상 기억"과 "키워드로 떠오름"을 나누고 작업기억 예산을 따로 뒀다. 엔진에는 이 구분이 없다.
- **예산 단위가 섞여 있다.** 기본은 UTF-8 **8000바이트**(한국어 약 2,600자), 설정하면 토큰 추정치. 한국어 RP는 같은 설정에서 영어보다 1/3만 들어간다.
- **기억 회상과 중복.** RP에서 기억 회상을 켜 두면 통합 기억과 별개로 과거 원문 조각이 또 들어간다(`generate.routes.ts` 기억 회상 분기에 `committedMemory` 조건이 없음). 같은 사건이 요약 + 원문으로 두 번 들어갈 수 있다.

### 2-2. 처리 효율

- 생성 한 번에 `loadCommittedMemory`가 **두 번** 호출되고(`committedMemoryForPrompt` 앞뒤), 그때마다 채팅의 **전체 메시지 목록**을 읽어 대조한다. 긴 채팅일수록 매 턴 비용이 커진다.
- 임베딩이 있으면 최대 512개 문서를 매 턴 점수 계산한다(캐시는 있음).

### 2-3. 정보 격리

- 공개 범위 처리는 보관함 규칙과 같다: 특정 인물에게만 생성할 때는 그 인물이 아는 것만, 병합 응답에서는 모두가 아는 것만 넣는다. 이 부분은 **문제 없음**.
- 다만 **고급 메모리를 켜면 통합 기억이 통째로 빠진다**(`activeChatSummary = advancedMemoryEnabled ? null : …`). 화면에서는 기억이 쌓여 보이는데 모델에는 안 들어가는 상태가 생길 수 있고, 안내가 없다.

### 2-4. 데이터 안전 (가장 시급)

- `readCommittedMemory`는 묶음 **하나라도** 형식이 어긋나면 **전체를 빈 기억으로** 돌려준다.
  읽기만 하면 원본은 남지만, 이어서 저장하는 경로(예: `setCommittedMemoryEnabled`의 `{ ...readCommittedMemory(m), enabled }`)는 그 빈 상태를 그대로 써서 **저장된 기억 전체를 덮어쓸 수 있다.**
  보관함은 "자동 변환·삭제 없음"을 원칙으로 했다. 실제 발생 여부는 미확인(재현 데이터 없음)이나, 코드상 가능하다.

## 4. 제안 (우선순위)

1. **데이터 안전**: 형식이 어긋난 묶음만 건너뛰고 나머지는 살린다. 저장 경로는 원본을 읽지 못하면 쓰지 않는다. 회귀 테스트로 고정.
2. **사실 주입 상한**: "항상 넣을 사실"과 "질의에 맞을 때만 넣을 사실"을 나누고(보관함의 앵커 구분), 진행 중 사실에도 개수·토큰 상한을 둔다. 약속은 기본 "항상", 나머지는 기본 "관련 있을 때".
3. **예산을 토큰 하나로 통일**: 바이트 기본값을 토큰 기본값으로 바꾸고 화면에 "약 N 토큰"을 보여 준다.
4. **중복 방지**: 통합 기억이 켜진 RP에서는 기억 회상을 기본으로 끄거나, 켜면 "같은 내용이 두 번 들어갈 수 있음"을 안내한다. 고급 메모리와 함께 켜면 통합 기억이 빠진다는 안내를 설정 화면에 띄운다.
5. **처리 효율**: 생성 한 번에 메시지 목록을 한 번만 읽도록 정리.
6. (선택) 검토 대기, 요소 기억의 별칭·호출 조건, 위키는 위 1~5 뒤에 범위를 정해 이식.

## 5. 결정 필요 (사용자)

- 제안 1~5를 다음 작업으로 진행할지.
- 사실 기본 정책: 약속만 "항상", 나머지는 "관련 있을 때"로 할지.
- 기억 회상(원문 조각)을 통합 기억과 함께 쓸지, 통합 기억이 켜지면 끌지.
- 보관함의 검토 대기·위키를 어디까지 이식할지.
