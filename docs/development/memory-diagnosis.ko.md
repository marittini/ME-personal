# 기억 기능 진단 보고서

작성: 2026-10-23 · 기준: `feat/next-update` · 비교 대상: 기억 보관함 확장 v2.1.1

이 문서는 **코드를 읽고 정리한 진단**이다. 실제 긴 채팅에서 토큰 사용량·속도를 재지는 않았다(미측정).
수정은 하지 않았다. 아래 "결정 필요"를 정한 뒤 작업한다.

## 1. 지금 엔진의 기억 구조

엔진에는 기억 계열 기능이 네 가지 있고, 서로 일부만 배타적이다.

| 기능                                        | 저장 위치                                   | 프롬프트에 들어가는 조건                                         |
| ------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------- |
| 통합 기억(`committedMemory`, 보관함 이식분) | 채팅 메타데이터 `committedMemory` 한 덩어리 | RP + 켜짐 + **고급 메모리 꺼짐**                                 |
| 기존 요약(`summary`/`summaryEntries`)       | 채팅 메타데이터                             | 통합 기억이 꺼졌을 때만                                          |
| 기억 회상(`enableMemoryRecall`, 벡터 조각)  | 메시지 임베딩                               | RP는 켰을 때, Convo는 기본 켜짐. **통합 기억과 무관하게** 들어감 |
| 고급 메모리(순정 `advancedMemory`)          | 별도                                        | 켜면 통합 기억·요약을 모두 끔                                    |

통합 기억의 흐름(`packages/server/src/services/committed-memory*.ts`):

1. 사용자가 "기억 정리"를 누르면 대기 메시지를 묶음(batch)으로 모델에 보내 요약·핵심(core)·사실(fact)을 받는다.
2. 사실은 종류(fact·promise·event·relationship·belief), 상태(current·resolved·uncertain), 진행도(약속), 공개 범위(audience)를 가진다.
3. 매 생성마다 `committedMemoryForPrompt`가 최근 메시지로 질의를 만들고, 글자 2-gram 겹침 점수(+ 임베딩이 있으면 코사인 0.35 이상)로 골라 넣는다.
4. 최근 30묶음은 요약, 300묶음까지는 core, 그 이전은 gist로 줄여 넣는다(`selectCommittedMemory`).

## 2. 문제점 (근거 코드 위치)

### 2-1. 컨텍스트 낭비

- **진행 중 사실은 질의와 상관없이 전부 후보가 되고, 개수 제한(topK)을 받지 않는다.**
  `selectCommittedMemory`에서 `reason: "current"` 항목은 기본 점수 2(약속 4)를 받아 항상 에피소드보다 먼저 예산을 채운다. topK 검사는 `reason !== "current"`에만 걸린다.
  사실이 쌓일수록 매 턴 같은 사실 묶음이 예산을 차지하고, 정작 관련 있는 과거 장면은 밀려난다.
  보관함은 "항상 기억"과 "키워드로 떠오름"을 나누고 작업기억 예산을 따로 뒀다. 엔진에는 이 구분이 없다.
- **예산 단위가 섞여 있다.** 기본은 UTF-8 **8000바이트**(한국어 약 2,600자), 설정하면 토큰 추정치. 한국어 RP는 같은 설정에서 영어보다 1/3만 들어간다.
- **기억 회상과 중복.** RP에서 기억 회상을 켜 두면 통합 기억과 별개로 과거 원문 조각이 또 들어간다(`generate.routes.ts` 기억 회상 분기에 `committedMemory` 조건이 없음). 같은 사건이 요약 + 원문으로 두 번 들어갈 수 있다.

### 2-2. 처리 효율

- 생성 한 번에 `loadCommittedMemory`가 **두 번** 호출되고(`committedMemoryForPrompt` 앞뒤), 그때마다 채팅의 **전체 메시지 목록**을 읽어 대조한다. 긴 채팅일수록 매 턴 비용이 커진다.
- 임베딩이 있으면 최대 512개 문서를 매 턴 점수 계산한다(캐시는 있음).

### 2-3. 정보 격리

- 공개 범위 처리는 보관함 규칙과 같다: 특정 인물에게만 생성할 때는 그 인물이 아는 것만, 병합 응답에서는 모두가 아는 것만 넣는다. 이 부분은 **문제 없음**.
- 다만 **고급 메모리를 켜면 통합 기억이 통째로 빠진다**(`activeChatSummary = advancedMemoryEnabled ? null : …`). 화면에서는 기억이 쌓여 보이는데 모델에는 안 들어가는 상태가 생길 수 있고, 안내가 없다.

### 2-4. 데이터 안전 (가장 시급)

- `readCommittedMemory`는 묶음 **하나라도** 형식이 어긋나면 **전체를 빈 기억으로** 돌려준다.
  읽기만 하면 원본은 남지만, 이어서 저장하는 경로(예: `setCommittedMemoryEnabled`의 `{ ...readCommittedMemory(m), enabled }`)는 그 빈 상태를 그대로 써서 **저장된 기억 전체를 덮어쓸 수 있다.**
  보관함은 "자동 변환·삭제 없음"을 원칙으로 했다. 실제 발생 여부는 미확인(재현 데이터 없음)이나, 코드상 가능하다.

## 4. 제안 (우선순위)

1. **데이터 안전**: 형식이 어긋난 묶음만 건너뛰고 나머지는 살린다. 저장 경로는 원본을 읽지 못하면 쓰지 않는다. 회귀 테스트로 고정.
2. **사실 주입 상한**: "항상 넣을 사실"과 "질의에 맞을 때만 넣을 사실"을 나누고(보관함의 앵커 구분), 진행 중 사실에도 개수·토큰 상한을 둔다. 약속은 기본 "항상", 나머지는 기본 "관련 있을 때".
3. **예산을 토큰 하나로 통일**: 바이트 기본값을 토큰 기본값으로 바꾸고 화면에 "약 N 토큰"을 보여 준다.
4. **중복 방지**: 통합 기억이 켜진 RP에서는 기억 회상을 기본으로 끄거나, 켜면 "같은 내용이 두 번 들어갈 수 있음"을 안내한다. 고급 메모리와 함께 켜면 통합 기억이 빠진다는 안내를 설정 화면에 띄운다.
5. **처리 효율**: 생성 한 번에 메시지 목록을 한 번만 읽도록 정리.
6. (선택) 검토 대기, 요소 기억의 별칭·호출 조건, 위키는 위 1~5 뒤에 범위를 정해 이식.

## 5. 결정 필요 (사용자)

- 제안 1~5를 다음 작업으로 진행할지.
- 사실 기본 정책: 약속만 "항상", 나머지는 "관련 있을 때"로 할지.
- 기억 회상(원문 조각)을 통합 기억과 함께 쓸지, 통합 기억이 켜지면 끌지.
- 보관함의 검토 대기·위키를 어디까지 이식할지.

## 6. 상세 설계 제안 (2026-10-23 18:08 · 구현 전 검토용)

목표: **보관함 v2.1.1의 운영 방식(항상/떠오름 분리, 예산, 검토 대기, 공개 범위)**을 엔진 통합 기억 위에 올린다.
기존 저장 데이터(`committedMemory` v1)는 지우거나 자동 변환하지 않고, 읽을 때 새 구조로 해석한다.

### 6-1. 추가로 확인한 점

- 정리(추출) 요청 때 모델에 기존 사실을 **최근 40개만** 보여 준다(`runCommittedMemory`의 `knownFacts.slice(-40)`).
  오래된 사실은 모델이 모르니 같은 대상을 새 사실로 다시 만들거나, 갱신해야 할 사실을 놓친다.
  (같은 종류·키·공개 범위면 나중에 합쳐지지만, 키가 조금만 달라도 중복이 남는다.)
- 보관함은 기억을 **엔진 로어북 항목으로 동기화**해서 넣었다(항상 항목 1개 + 키워드 항목 여러 개).
  그래서 순정 로어북의 키워드 판정·예산·삽입 위치를 그대로 썼다. 엔진 통합 기억은 자체 검색을 쓴다.

### 6-2. 기억 계층 (무엇을, 언제 넣는가)

| 계층           | 내용                                          | 넣는 조건                                                            | 예산                                                                                                          |
| -------------- | --------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| A. 항상        | 진행 중 약속, 사용자가 "항상"으로 고정한 사실 | 매 턴                                                                | 별도 예산(기본 약 600토큰). 넘치면 우선순위 낮은 것부터 **대기**(지우지 않음, 화면에 "예산 때문에 대기" 표시) |
| B. 떠오름      | 그 밖의 현재 사실(소유·위치·관계·취향·상태)   | 최근 대화가 키워드·조합 조건에 맞거나 임베딩 유사도가 기준 이상일 때 | 개수 상한(기본 12) + 토큰 예산                                                                                |
| C. 이야기 흐름 | 묶음 요약(최근)·core(중간)·gist(오래됨)       | 최근 N묶음은 항상, 그 이전은 관련 있을 때                            | 남은 예산                                                                                                     |

- 사실마다 `activation: "always" | "recall"` 필드를 둔다. 기본값: 약속 = always, 나머지 = recall. 사용자가 바꿀 수 있다.
- 지금은 B 계층이 사실상 A처럼 동작한다(진행 중 사실 전부가 후보, 개수 제한 없음). 이게 컨텍스트 낭비의 주원인이다.
- 예산은 **토큰 하나로 통일**. 화면에 "이번 턴 약 N 토큰: 항상 a / 떠오름 b / 흐름 c"로 보여 준다.

### 6-3. 떠오름 판정 (보관함의 요소 기억 방식)

- 사실(또는 대상)마다 **식별용 별칭**과 **호출 조건**을 나눈다.
  - 별칭: 같은 대상인지 판단할 때만 씀(예: "리암", "Liam", "도련님").
  - 호출 키워드: 하나만 나와도 떠오름. 일반 명사(예: "사물함")는 단독 키워드로 쓰지 않는다.
  - 조합 조건: 한 줄의 단어가 **모두** 나와야 떠오름(예: "지희 + 사물함").
- 판정 순서: 키워드·조합 일치 → (임베딩이 있으면) 유사도 보정 → 점수순으로 상한까지.
- 한국어·영어 RP 모두 떠오르도록 키워드는 원문 언어와 한국어를 함께 둔다(지금 추출 지시와 같음).

### 6-4. 대상별 현재 사실 (요소 기억)

- 같은 대상(인물·물건·장소)의 사실은 한 묶음으로 관리: **현재 사실 최대 8개**, 넘치면 오래된 것부터 **이력**으로 이동(삭제 아님).
- 갱신은 "현재 사실 교체 + 이전 값은 이력에 누적". 지금 있는 `previous` 버전 기록을 그대로 활용한다.

### 6-5. 추출 품질

- 정리 요청에 넣는 기존 사실을 "최근 40개"가 아니라 **이번 묶음과 관련 있는 사실**로 고른다: 이번 묶음의 키워드·별칭과 겹치는 사실 우선 + 진행 중 약속 전부.
- 모델 결과는 바로 확정하지 않고 **검토 대기**에 둔다(보관함처럼).
  - 새 항목은 기본 선택, 기존 항목의 변경은 기본 미선택, 동일 항목은 잠금.
  - "자동 적용" 설정을 켜면 바로 확정하되, 최근 자동 적용은 되돌리기 가능.
- 근거 메시지가 수정·삭제되면 해당 기억을 "근거 바뀜"으로 표시(지금의 invalidated 처리 유지 + 화면 안내).

### 6-6. 정보 격리

- 공개 범위 규칙은 지금 것을 유지한다: 특정 인물 생성 = 그 인물이 아는 것만, 병합 응답 = 모두가 아는 것만, 범위 없는 비밀 = 넣지 않음.
- 추가: 특정 인물에게 숨긴 메시지는 그 인물의 기억 근거로 쓰지 않는다(보관함 v2.1.0 규칙). 엔진의 메시지 숨김 정보로 판정.
- 분기: 분기 채팅은 부모 기억을 복사하지 않고 "분기 시점까지 공유, 이후 분리"로 본다(지금 `ownerChatId` 검사 유지).
- 재생성: 재생성 대상 이후 메시지에 근거한 기억은 넣지 않는다(지금 구현됨, 유지).

### 6-7. 다른 기억 기능과의 관계

- **고급 메모리(순정)**와 동시에 켜면 통합 기억이 빠진다 → 설정 화면에서 둘 중 하나만 고르게 하고, 켜져 있는 쪽을 표시.
- **기억 회상(원문 조각)**: 통합 기억이 켜진 RP에서는 기본으로 끈다. 사용자가 켜면 "같은 내용이 두 번 들어갈 수 있음" 안내.
- **기존 요약**: 통합 기억이 켜지면 이미 빠진다(유지).
- **Lorebook Keeper**: 보관함은 기억 로어북 항목을 잠가 Keeper가 덮어쓰지 못하게 했다. 6-8에서 로어북 방식을 고르면 같은 잠금이 필요하다.

### 6-8. 넣는 방식: 자체 검색 vs 로어북 동기화 (결정 필요)

|      | 자체 검색(지금)                                       | 로어북 동기화(보관함 방식)                                                        |
| ---- | ----------------------------------------------------- | --------------------------------------------------------------------------------- |
| 장점 | 공개 범위·재생성 제외를 정확히 처리. 임베딩 사용 가능 | 순정 로어북의 판정·삽입 위치·예산을 그대로 씀. 사용자가 로어북 화면에서 직접 확인 |
| 단점 | 판정 규칙을 따로 유지해야 함                          | 공개 범위·재생성 제외 표현이 어렵다. Keeper 충돌 관리 필요                        |

제안: **자체 검색을 유지**하고, 6-2~6-4의 계층·예산·호출 조건을 자체 검색에 넣는다. 로어북은 "보기·내보내기" 용도로만 선택 제공.

### 6-9. 데이터·성능

- 저장 형식 v2: v1을 읽어 메모리 안에서만 v2로 해석(`activation` 기본값 등). 사용자가 기억을 수정해 저장할 때 v2로 쓴다. v1 원본은 처음 v2로 쓰기 전에 백업 필드에 한 번 남긴다.
- 형식이 어긋난 묶음은 건너뛰고 나머지는 살리며, 원본을 읽지 못하면 쓰지 않는다(2-4의 데이터 안전).
- 생성 한 번에 메시지 목록·기억을 한 번만 읽는다. 메시지 지문 대조는 바뀐 부분만.

### 6-10. 화면 (보관함 구성 참고)

- 개요: 이번 턴에 들어간 기억(이미 있는 `committedMemoryReceipt` 활용)과 토큰 막대, 검토 대기 개수, 예산 때문에 대기 중인 항목.
- 약속 / 사실(대상별) / 흐름 탭. 각 항목에 "항상/떠오름" 전환, 키워드·조합 조건 편집, 근거 메시지로 이동.
- 이야기 위키는 이번 범위에서 제외(필요하면 후속).

### 6-11. 검증 계획

- 회귀: v1 데이터 읽기·형식 오류 묶음 건너뛰기·쓰기 거부, 계층별 예산, 키워드·조합 판정, 공개 범위, 재생성 제외.
- 실제 긴 RP 하나로 수정 전후 프롬프트 토큰 비교(측정값을 노트에 기록).

### 6-12. 결정 필요

1. 넣는 방식: 자체 검색 유지(제안) / 로어북 동기화
2. 사실 기본값: 약속만 항상(제안) / 다른 기준
3. 검토 대기를 기본으로 할지, 자동 적용을 기본으로 할지
4. 기억 회상과 고급 메모리를 통합 기억과 배타로 묶을지
5. 예산 기본값(항상 600토큰, 떠오름 12개)이 적절한지
